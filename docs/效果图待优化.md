# 效果图待优化

创建日期：2026-07-16

本文档用于推进“效果图生成模块”从当前可用版本升级到正式生产版本。

推进方式：

```text
1. 每次只做一个明确步骤。
2. 每一步写清楚为什么做、改哪里、怎么验证。
3. 用户确认后再进入下一步。
4. 不把 AI 装修顾问代码和效果图生成代码混在一起。
5. 不使用 mock 效果图。
```

## 1. 当前模块现状

当前已经具备：

```text
1. 户型图上传。
2. 户型图真实解析。
3. 解析完成后生成“平面户型 · 立体图”。
4. 引导式生成意图。
5. 生成 2D 全屋覆盖封面图。
6. 2D / 3D 模式切换。
7. 生成全屋 3D 立体图。
8. 单空间 2D / 3D 按需生成。
9. 空间图参考全屋覆盖封面图生成。
10. 放大预览和旋转。
11. 生图结果写入 design_renders。
```

当前主要问题：

```text
1. 生图接口仍偏同步，接口内等待 DashScope 任务完成，正式环境不够稳。
2. 任务状态不够细，用户不知道卡在哪一步。
3. 单张图失败后的重试能力还不完整。
4. 生成历史、删除、下载、对比等管理能力不足。
5. 图片存储还需要正式化，比如 OSS/CDN/缩略图策略。
6. Prompt 没有版本管理，后续效果变化难追溯。
7. 用户权限隔离还需要补齐，正式上线不能所有项目混在一起。
8. 监控日志不足，无法清晰统计失败率、耗时和成本。
9. 效果图还没有转成可报价的材料清单和工程项，暂时不能输出正式报价。
```

## 2. 正式版目标

正式版效果图生成模块应该做到：

```text
1. 用户上传户型图后，流程清晰、状态明确。
2. 生图任务不会因为耗时长导致接口崩溃或页面一直卡住。
3. 每张图都有清晰来源：模型、prompt、参考图、用户偏好、户型解析结果。
4. 失败可以重试，不影响已经生成成功的图片。
5. 用户可以管理生成结果：查看、下载、删除、重新生成。
6. 系统能控制请求数量和成本。
7. 图片稳定可访问，适合部署到正式服务器。
8. 后续接入更强模型时，代码结构不用大改。
9. 效果图方案可以进一步沉淀为材料清单、工程量清单和报价单。
```

## 3. 优化阶段总览

### 第 1 阶段：正式任务系统

目标：

```text
把“接口内等待生图完成”改造成更正式的任务流。
```

要解决：

```text
1. 生成慢时页面一直等待。
2. DashScope 超时后任务状态不清晰。
3. 单张图失败无法独立重试。
4. 前端无法展示更细的任务进度。
```

阶段结果：

```text
用户点击生成后，先创建任务。
前端看到明确状态。
后端按任务执行生图。
失败可以针对单张图重试。
```

### 第 2 阶段：生成结果管理

目标：

```text
让用户能管理已经生成的效果图。
```

要做：

```text
1. 删除某张效果图。
2. 重新生成某张效果图。
3. 下载效果图。
4. 设为封面。
5. 查看生成时间、模式、空间名称。
```

### 第 3 阶段：存储正式化

目标：

```text
让图片存储适合正式部署。
```

要做：

```text
1. 梳理当前本地 uploads 目录。
2. 规划阿里 OSS 或服务器静态资源目录。
3. 增加缩略图策略。
4. 增加无效图片清理策略。
5. 确保线上图片 URL 稳定访问。
```

### 第 4 阶段：Prompt 版本化和追溯

目标：

```text
让每张图片都能追溯“为什么这样生成”。
```

要做：

```text
1. 增加 prompt_version。
2. 保存完整 prompt。
3. 保存模型参数。
4. 保存参考图信息。
5. 保存户型解析摘要。
6. 保存用户生成偏好。
```

### 第 5 阶段：用户隔离和权限

目标：

```text
正式上线后，不同用户只能看到自己的户型图、项目和效果图。
```

要做：

```text
1. design_projects 增加 user_id 或 owner_id。
2. 所有查询按 user_id 过滤。
3. 所有生成接口校验项目归属。
4. 前端只展示当前用户项目。
```

### 第 6 阶段：监控、日志和成本控制

目标：

```text
让系统能发现问题、定位问题、控制成本。
```

要做：

```text
1. 记录每次生图耗时。
2. 记录 DashScope task_id 和失败原因。
3. 统计失败率。
4. 限制重复点击。
5. 限制短时间重复生成。
6. 后台查看任务列表。
```

### 第 7 阶段：效果图报价系统

目标：

```text
把效果图方案进一步转成可编辑、可追溯、可计算的全屋报价单。
```

核心判断：

```text
效果图不能直接等于报价。
效果图只能表达风格、空间氛围、材料倾向和设计配置。
正式报价必须基于：
1. 户型面积。
2. 空间列表。
3. 材料清单。
4. 工程项。
5. 工程量。
6. 单价。
7. 管理费、税费、损耗和服务费规则。
```

要做：

```text
1. 从户型解析结果得到空间、面积、厨卫、阳台、门窗等基础数据。
2. 从效果图方案提取材料倾向，例如地板、瓷砖、乳胶漆、柜体、灯具、软装。
3. 按空间生成材料清单。
4. 按空间生成工程项清单。
5. 根据面积、延米、数量计算工程量。
6. 根据材料档位和单价库计算报价。
7. 输出全屋报价单。
8. 允许用户或商家调整材料品牌、档位、单价和是否包含软装家电。
```

阶段结果：

```text
用户生成效果图后，可以点击“生成报价单”。
系统根据户型、效果图方案、材料配置和工程规则输出一份报价草稿。
报价草稿可编辑、可下载、可追溯。
```

## 4. 第 7 阶段：报价系统思路

报价系统暂时作为后续独立阶段，不和当前生图任务系统混在一起。

### 4.1 正确链路

```text
上传户型图
-> AI 解析户型：面积、空间、门窗、厨卫、阳台
-> 生成全屋效果图方案
-> 结构化效果图方案：风格、材料倾向、空间配置
-> 按空间生成材料清单
-> 按空间生成工程项清单
-> 根据面积/数量/延米计算工程量
-> 套用材料单价和施工单价
-> 生成全屋报价单
```

### 4.2 为什么不能直接看图报价

```text
效果图可以看出：
1. 装修风格。
2. 大致材料倾向。
3. 是否有柜体、吊顶、灯带、软装。
4. 空间氛围和设计复杂度。

但效果图不能精确知道：
1. 地板多少平方米。
2. 墙面乳胶漆多少平方米。
3. 瓷砖铺贴多少平方米。
4. 柜体多少延米。
5. 吊顶多少平方米。
6. 水电改造多少米。
7. 防水多少平方米。
8. 材料品牌和等级。
9. 是否含人工、辅材、管理费和税费。
```

结论：

```text
AI 可以生成报价草稿，但不能只靠一张效果图直接给最终报价。
正式报价必须让用户或商家确认材料、工程项、单价和计价规则。
```

### 4.3 建议新增数据表

```text
design_quote_templates
报价模板。
用于区分经济、标准、品质、高端等报价档位。

design_material_items
材料库。
记录材料名称、分类、单位、默认单价、品牌、档位、适用空间。

design_work_items
工程项库。
记录施工项目、单位、默认人工单价、辅材规则和适用空间。

design_quotes
报价单主表。
关联 project、floor_plan、generation_job，可记录总价、状态、报价版本。

design_quote_items
报价明细。
记录空间、材料项、工程项、单位、数量、单价、小计、备注。
```

```

```

```text

```

```text

```

```text

```

```text

7. 可下载报价单。
```

### 4.6 报价计算公式

基础公式：

```text
明细小计 = 数量 × 单价
空间小计 = 当前空间所有明细小计之和
分类小计 = 当前分类所有明细小计之和
直接费用 = 所有明细小计之和
管理费 = 直接费用 × 管理费比例
税费 = (直接费用 + 管理费) × 税率
报价总价 = 直接费用 + 管理费 + 税费
```

工程量示例：

```text
地面工程量 = 空间地面面积 × 损耗系数
墙面工程量 = 空间周长 × 层高 - 门窗面积
顶面工程量 = 空间顶面面积
柜体工程量 = 柜体延米
防水工程量 = 卫生间/厨房/阳台地面面积 + 墙面上翻面积
```

### 4.7 AI 在报价中的角色

AI 应该做：

```text
1. 根据户型解析结果推算空间工程量。
2. 根据效果图提取材料倾向和配置等级。
3. 根据报价模板生成材料清单草稿。
4. 根据工程项库生成施工清单草稿。
5. 标记不确定项，提醒用户确认。
```

AI 不应该做：

```text
1. 不应该只看图片直接给最终价格。
2. 不应该绕过材料单价库和工程项库。
3. 不应该把不确定数据包装成确定报价。
4. 不应该替代商家最终报价确认。
```

### 4.8 报价系统实施顺序

建议后续按这个顺序做：

```text
Step 1：建立报价数据结构。
Step 2：建立材料库和工程项库。
Step 3：根据户型解析结果生成空间工程量草稿。
Step 4：根据效果图方案生成材料清单草稿。
Step 5：生成报价单主表和明细。
Step 6：前端展示报价配置页。
Step 7：前端展示报价结果页。
Step 8：支持编辑、下载和重新计算。
```

## 5. 第 1 阶段详细步骤

第 1 阶段先做“正式任务系统”，这是后续正式化的地基。

### Step 1：梳理当前任务状态

目的：

```text
先明确当前 design_generation_jobs 和 design_renders 能不能支撑正式任务流。
```

需要检查：

```text
1. design_generation_jobs 当前字段。
2. design_renders 当前字段。
3. 现有生成接口如何写入 status/progress/error_message。
4. 前端如何根据 generationJob 展示状态。
```

预计改动：

```text
只补文档和字段说明。
先不改业务逻辑。
```

确认标准：

```text
我们能明确知道：
1. 当前有哪些状态。
2. 哪些状态不够用。
3. 下一步需要补哪些字段或表。
```

### Step 2：定义正式任务状态枚举

目的：

```text
让前端和后端使用同一套状态语言。
```

建议状态：

```text
pending：任务已创建，等待执行。
running：任务执行中。
succeeded：当前图片生成成功。
failed：当前图片生成失败。
canceled：任务取消。
retrying：正在重试。
```

确认标准：

```text
文档中明确状态枚举。
代码中不再出现前端后端状态含义不一致。
```

### Step 3：拆分“生成任务”和“生成图片”

目的：

```text
一次用户点击可能对应多张图片。
正式版需要区分：
1. 整体任务。
2. 单张图片任务。
```

当前情况：

```text
design_generation_jobs 表示一次整体生成任务。
design_renders 表示最终图片结果。
```

可能需要新增：

```text
design_render_tasks
```

用途：

```text
记录每一张图片的生成过程。
例如：
全屋覆盖封面图任务
客厅 2D 任务
卧室 2D 任务
全屋 3D 任务
```

确认标准：

```text
单张图失败时，不影响整个 project。
用户可以只重试失败的那一张图。
```

### Step 4：接口改成任务优先

目的：

```text
用户点击生成后，接口先创建任务记录，再执行或等待后台执行。
```

当前接口：

```text
POST /api/design/jobs
POST /api/design/jobs/[id]/spaces
```

优化方向：

```text
1. 创建任务。
2. 返回 taskId/jobId。
3. 前端进入生成中。
4. 后端执行生图。
5. 前端轮询任务状态。
```

确认标准：

```text
前端不再因为 DashScope 慢而一直卡在同一个请求里。
```

### Step 5：前端展示细化进度

目的：

```text
用户能知道当前卡在哪一步。
```

建议展示：

```text
户型上传中
户型解析中
户型结构图生成中
全屋覆盖封面图生成中
空间图生成中
生成成功
生成失败，可重试
```

确认标准：

```text
页面不再只有笼统的“生成中”。
```

### Step 6：失败重试

目的：

```text
正式版不能因为一张图失败就让用户重头开始。
```

要做：

```text
1. 全屋覆盖封面图失败，可以重新生成全屋覆盖封面图。
2. 某个空间图失败，可以只重试该空间。
3. 3D 图失败，可以只重试 3D。
4. 重试时保留原 project 和 floorPlan。
```

确认标准：

```text
失败图片旁边出现“重新生成”。
点击后只重试当前图片，不影响已成功图片。
```
