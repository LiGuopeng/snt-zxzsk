# 效果图生成模块实施方案

## 模块定位

效果图生成是独立于 AI 装修顾问的业务模块。

- AI 装修顾问：负责知识库问答、施工风险、材料建议、预算合同等咨询。
- 效果图生成：负责上传户型图、解析户型、生成全屋效果图、展示生成结果。

两个模块在页面和代码上保持边界清晰。当前版本效果图生成模块只负责出图主流程，不接入知识库检查和风险提醒。

知识库检查可以作为后期可选能力，但不是当前版本必须功能。如果后续重新启用，也不需要为效果图重新建设一套独立知识库，应复用现有装修知识库，并且不能把知识库聊天界面混入效果图生成页面。

## 当前产品原则

1. 户型图必传。
2. 按户型图自动解析空间，不让用户手动勾选客厅、卧室、厨房等空间。
3. 生成目标是全屋效果图，不是单个局部空间图。
4. 用户用自然语言描述偏好，系统自动提取风格、预算、色系、家庭情况等参数。
5. 初始化页面不展示假户型、假方案、假效果图、假队列。
6. 未上传户型图前，生成按钮禁用。
7. 生成结果支持多视角缩略图和放大查看。
8. 当前版本不使用 mock 图片，生成结果必须来自真实生图服务。
9. 生成状态必须完整：未生成、生成中、生成失败、已完成；已完成后允许重新生成，重新生成时保留旧结果，等待新结果完成后替换。
10. 错误体验必须闭环：上传前校验文件格式和大小，解析失败允许重新解析，生成失败允许重新生成，图片加载失败要显示兜底提示。
11. 当前生成策略为先生成 `全屋效果图`，再按用户点击生成对应空间效果图，结果保存到 Supabase Storage 后再展示。
12. 知识库检查和风险提醒不纳入当前版本主流程，后期如有需要再作为可选能力接入。
13. 上传户型图解析完成后，首张全屋图固定使用默认风格生成，不让用户先配置风格。
14. 全屋图的目标不是普通室内摄影图，而是三维俯视/轴测的完整户型全屋总览。
15. 各空间效果图使用 2D 室内效果图视角，不使用全屋 3D 轴测视角。

## 变更记录

### 2026-07-09：固定首张全屋图为 3D 轴测全屋总览

本次调整目标：

- 用户上传户型图并解析完成后，先生成一张固定默认风格的全屋总览图。
- 默认风格为现代简约、明亮通透、暖白浅木色、真实家具软装。
- 全屋效果图必须展示完整户型，包含所有主要空间、墙体、门洞、窗洞、地面、家具、厨卫和阳台关系。
- 全屋效果图采用三维俯视/轴测视角，类似从户型图转成可视化 3D 全屋模型。

边界说明：

- 全屋图不是普通客厅、卧室等单空间照片。
- 全屋图不是 2D 平面户型图、施工图或手绘图。
- 空间效果图仍按用户点击的具体空间单独生成，例如客厅、主卧、厨房。
- 目前不开放用户手动选择风格，避免首轮流程变复杂；后期可作为高级设置再补充。

### 2026-07-09：首轮生图切换为快出图模式

本次调整目标：

- 当前阶段优先验证上传、解析、生成、展示的完整链路，首图需要尽快返回。
- 默认生图模型继续使用 `wan2.7-image`，不切换到更慢的 pro 模型。
- 默认尺寸从 `2K` 调整为 `1K`，降低等待时间。
- 默认关闭 `DASHSCOPE_IMAGE_THINKING_MODE`，减少首轮生成耗时。

产品策略：

- 首轮生成用于快速判断空间关系和整体方案是否正确。
- 后期可以增加“高清重绘”能力，再用 `2K` 或更高质量参数生成最终图。
- 空间效果图继续按用户点击后单独生成，避免一次性生成多张导致等待过久。

### 2026-07-09：明确全屋与空间图的视角边界

本次调整目标：

- 全屋总览图：使用 3D 俯视/轴测视角，展示完整户型、空间关系和整体风格。
- 各空间效果图：使用 2D 室内效果图视角，展示单个房间或功能区的装修效果。

实现边界：

- 全屋总览图不生成普通单房间照片。
- 空间效果图不生成全屋 3D 俯视模型。
- 空间图仍然继承全屋默认风格、色系和材质方向，保证视觉方案统一。

### 2026-07-09：升级户型图 AI 解析结构

本次升级目标：

- 上传户型图后，AI 不只识别户型和空间列表，还要输出更适合后续“户型诊断、空间图生成、3D 建模”的结构化数据。
- 每次能力变更必须记录到本文档，避免后续产品方向和实现状态脱节。

当前 AI 解析能力：

- `house_type`：户型摘要，例如 3室2厅1卫。
- `area`：总面积，依赖户型图是否标注。
- `spaces`：空间列表，包括空间名称、空间类型、置信度、估算面积、面积占比、相邻连接空间。
- `doors`：门的位置、连接空间、置信度。
- `windows`：窗的位置、关联空间、朝向或图纸方向、置信度。
- `walls`：墙体位置、疑似类型、置信度和说明。
- `wet_areas`：厨卫等湿区位置。
- `balconies`：阳台位置及关联空间。
- `circulation`：动线文字说明。
- `circulation_analysis`：动线总结、问题列表、评分。
- `area_ratio_analysis`：面积比例总结、疑似浪费点、优化建议。
- `orientation`：朝向或采光判断。
- `structure_risk_warnings`：结构安全边界提醒。
- `warnings`：模型无法确认的信息和原因。

安全边界：

- 普通户型图通常不能可靠判断承重墙、梁柱和结构安全。
- AI 只能输出 `unknown`、`load_bearing_candidate`、`non_load_bearing_candidate` 等疑似判断。
- 拆改、承重、梁柱等结论必须以结构图、物业审批和专业人员判断为准。

当前存储方式：

- 基础字段继续回填到 `design_floor_plans.house_type`、`area`、`spaces`、`circulation`。
- 完整解析 JSON 保存到 `design_floor_plans.analysis_result`。
- 前端当前仍只展示基础户型、面积、空间、动线；高级字段先作为后续户型诊断和 3D 能力的数据基础。

### 2026-07-09：新增户型诊断面板

本次升级目标：

- 将 `analysis_result` 中已经保存的高级解析字段展示到页面上。
- 用诊断面板替换旧的“全屋方案检查结果”占位卡片。
- 当前不接知识库风险检查，只展示户型图本身的解析诊断。

当前展示内容：

- 动线：展示 `circulation_analysis.summary` 和动线问题。
- 面积：展示 `area_ratio_analysis.summary`、疑似浪费点和优化建议。
- 门窗采光：展示门位数量、窗位数量和朝向/采光判断。
- 结构边界：展示 `structure_risk_warnings`，明确承重墙和梁柱不能只靠普通户型图确定。

兼容策略：

- 旧数据如果没有高级解析字段，页面显示“待解析后生成”或基础字段兜底。
- 高级字段仍从 `design_floor_plans.analysis_result` 读取，不新增表。

## 后期可选能力

### 1. 效果图方案接入现有知识库

当前结论：

- 当前版本不需要使用知识库能力。
- 不需要重新建设一套效果图专用知识库。
- 不把 AI 装修顾问聊天窗口混入效果图生成模块。
- 如果后期重新启用，知识库检查应作为效果图生成后的结构化检查步骤。

知识库在效果图模块中的职责：

- 检查生成方案的施工风险。
- 检查材料选择是否合理。
- 检查预算风险和落地成本。
- 根据户型解析结果给空间优化建议。
- 根据用户需求提醒收纳、儿童安全、采光、动线等问题。

建议流程：

```text
生成全屋效果图
-> 整理方案摘要
-> 调用现有装修知识库
-> 生成结构化检查报告
-> 写入 design_reviews
```

结构化检查报告建议包含：

- `risk_summary`：整体风险摘要。
- `construction_risks`：施工风险。
- `material_suggestions`：材料建议。
- `budget_risks`：预算风险。
- `space_suggestions`：空间优化建议。
- `confidence`：检查置信度。

页面表现建议：

- 不展示聊天输入框。
- 不展示知识库对话历史。
- 只展示“全屋方案检查结果”。
- 结果可以分为施工、材料、预算、空间建议四块。
- 后期可以加“重新检查”按钮，但必须基于当前方案生成报告。

## 初始页面状态

用户首次进入效果图生成页时：

- 户型图状态：待上传。
- 户型解析：户型待识别、面积待识别、空间待识别、动线待识别。
- AI 生成意图：输入框为空，只展示 placeholder。
- 示例需求：
  - 现代简约 · 明亮通透 · 有小孩
  - 奶油风 · 温柔耐看 · 收纳多
  - 原木风 · 自然放松 · 预算中等
- 全屋效果图方案：展示空状态，不展示假效果图。
- 生成队列：等待上传户型图后创建。
- 生成按钮：禁用。

## 用户主流程

1. 用户进入效果图生成模块。
2. 用户上传户型图。
3. 系统上传文件到 Supabase Storage。
4. 系统创建或更新设计项目。
5. 系统解析户型图，得到户型、面积、空间、动线等信息。
6. 用户输入自然语言生成意图，或点击示例需求。
7. 用户点击生成全屋效果图。
8. 后端创建生成任务。
9. 前端轮询任务状态。
10. 生成完成后展示全屋效果图、多空间视角图和方案说明。
11. 用户可以切换视角并放大查看生成结果。

## 当前阶段：真实效果图生图

当前版本不再使用 mock 效果图。

生成链路：

```text
户型图解析结果
-> 用户生成意图
-> 拼接全屋装修效果图 prompt
-> 调用真实生图服务
-> 图片上传 Supabase Storage
-> 写入 design_renders
-> 前端展示结果
```

要求：

- 未配置真实生图服务时，接口必须返回明确错误，不能返回假图。
- 生图失败时，生成任务状态必须变成 `failed`。
- 生成成功后，图片必须保存到 `design-assets/renders/{project_id}/...`。
- `design_renders.image_url` 必须指向 Supabase Storage 里的真实生成图片。
- 点击“生成全屋效果图”时，只生成一张 `全屋 · 全屋效果图`，保证首个结果尽快出现。
- 全屋图生成完成后，页面展示户型解析出的空间列表。
- 用户点击某个空间后，再单独生成该空间效果图。
- 空间图不默认全部生成，避免首轮等待过长和额度浪费。

## 当前阶段：错误体验完整化

效果图生成模块的错误处理必须围绕主流程设计，不展示技术栈内部错误给用户。

### 上传错误

处理要求：

- 前端上传前校验文件类型，只允许 JPG、PNG、WEBP、PDF。
- 前端上传前校验文件大小，不能超过 15MB。
- 后端继续保留同样的文件类型和大小校验，避免绕过前端。
- 上传失败后显示明确错误，用户可以重新选择文件上传。

### 解析错误

处理要求：

- 上传成功后自动进入“解析中”。
- PDF 当前可以上传保存，但暂不支持真实解析，必须明确提示用户上传 JPG、PNG 或 WEBP。
- 视觉模型、网络、接口异常导致解析失败时，户型图状态变成“解析失败”。
- 解析失败后保留已上传文件，提供“重新解析”入口。
- 用户也可以重新上传更清晰的户型图。

### 生成错误

处理要求：

- 未完成户型解析时不能生成。
- 创建生成任务失败时，生成队列状态显示“生成失败”。
- 生成完成但没有返回效果图时，提示用户重新生成。
- 已经生成过结果后再次重新生成，旧图先保留，新结果完成后再替换。

### 图片加载错误

处理要求：

- 主效果图加载失败时显示“图片加载失败”兜底层。
- 缩略图加载失败时在卡片标题提示加载失败。
- 放大预览加载失败时显示兜底提示，允许关闭后切换视角或重新生成。

## 当前阶段：结果展示真实感

真实生图结果也要符合产品展示规则。

### 空间视角生成规则

处理要求：

- 永远生成一张 `全屋 · 全屋总览视角`，作为方案主图。
- 空间视角来自户型解析结果，不写死固定空间。
- 相同类型空间需要去重，例如多个客厅识别结果只保留一个核心视角。
- 空间按家庭决策优先级排序：客厅、餐厅、主卧、卧室、厨房、卫生间、书房、阳台。
- 如果解析出的空间太少，补足客餐厅、主卧、厨房等核心视角，避免结果区过空。
- 如果解析出的空间太多，最多展示 6 个空间视角，避免底部横向区域过乱。

### 视角命名规则

处理要求：

- 不使用“主视角”“空间视角”这类过泛的命名。
- 客厅优先展示为 `客餐厅联动视角`。
- 餐厅优先展示为 `餐厨联动视角`。
- 主卧展示为 `睡眠区主视角`。
- 厨房展示为 `烹饪动线视角`。
- 卫生间展示为 `干湿分区视角`。
- 书房展示为 `书桌收纳视角`。
- 阳台展示为 `休闲阳台视角`。

### 前端展示规则

处理要求：

- 结果头部展示当前视角名。
- 结果标签展示已生成、视角数量、空间匹配。
- 缩略图使用横向滑动轨道，不使用多行网格。
- 缩略图标题使用 `空间 · 视角`，避免连字符带来的后台感。

## 页面流程与数据表对应关系

效果图生成模块的数据结构必须按页面操作流程理解，避免后端表设计和用户使用路径脱节。

- 文件地址。
- 上传状态。
- 解析状态。
- 解析结果。

### 页面顺序 2：AI 生成意图

### 页面流程顺序

```text
上传户型图 -> AI 生成意图 -> 户型解析 -> 生成任务 -> 效果图结果 -> 知识库检查
```

### 数据库建表顺序

页面上虽然先上传户型图，但数据库里户型图需要挂到项目上，所以必须先建项目表。

```text
design_projects -> design_floor_plans -> design_generation_jobs -> design_renders -> design_reviews
```

## 前端状态设计

效果图生成页建议至少支持以下状态：

- `idle`：未上传户型图。
- `uploaded`：户型图已上传，等待解析。
- `analyzing`：正在解析户型图。
- `ready`：解析完成，可生成。
- `generating`：正在生成效果图。
- `completed`：生成完成。
- `failed`：上传、解析或生成失败。

## 数据表建议

### design_projects

保存一次全屋设计生成项目。

用途说明：

- 这是效果图生成模块的主表。
- 页面上用户每发起一次全屋效果图生成，都应该对应一条项目记录。
- 它负责串联户型图、生成任务、效果图结果和知识库检查结果。
- 用户输入的 AI 生成意图、系统抽取出的风格预算色系、项目当前状态都存在这里。

对应页面环节：

- AI 生成意图。
- 当前项目状态。
- 生成按钮是否可用。
- 后续结果归属。

为什么需要：

- 户型图、生成任务、效果图、知识库检查都需要挂在同一个项目下面。
- 没有项目主表，后续很难判断某张效果图属于哪一次用户生成。

字段建议：

- `id`：项目 ID，主键。
- `user_id`：用户 ID，后续做登录和用户隔离时使用。
- `title`：项目标题，例如“我的新家全屋方案”。
- `status`：项目状态，例如 `draft`、`ready`、`generating`、`completed`、`failed`。
- `intent_text`：用户输入的自然语言生成需求。
- `style`：系统从需求中抽取出的风格，例如现代简约、奶油风。
- `budget_level`：系统从需求中抽取出的预算等级，例如经济、中等、品质。
- `color_palette`：系统从需求中抽取出的全屋色系，例如暖白原木。
- `house_type`：户型解析结果摘要，例如 3室2厅1卫。
- `area`：户型面积。
- `created_at`：创建时间。
- `updated_at`：更新时间。

### design_floor_plans

保存用户上传的户型图。

用途说明：

- 保存户型图文件和户型解析结果。
- 页面上用户上传的每一张户型图都对应一条记录。
- 解析出来的户型、面积、空间列表、动线信息都存在这里。

对应页面环节：

- 上传户型图。
- 户型解析。
- 右侧户型解析结果。
- 生成任务的输入依据。

为什么需要：

- 户型图是效果图生成的必传条件。
- 生成任务必须基于户型解析结果创建。
- 后续如果用户重新上传户型图，也需要保留文件和解析状态。

字段建议：

- `id`：户型图 ID，主键。
- `project_id`：所属项目 ID，关联 `design_projects.id`。
- `file_url`：户型图在 Supabase Storage 中的访问地址。
- `file_name`：原始文件名。
- `file_type`：文件类型，例如 `image/png`、`image/jpeg`、`application/pdf`。
- `file_size`：文件大小。
- `analysis_status`：解析状态，例如 `pending`、`analyzing`、`completed`、`failed`。
- `analysis_result`：户型解析原始 JSON，包含空间、面积、动线等结构化信息。
- `created_at`：创建时间。

### design_generation_jobs

保存效果图生成任务。

用途说明：

- 保存每一次点击“生成全屋效果图”后创建的任务。
- 任务状态、进度、prompt、错误原因都存在这里。
- 前端生成队列和轮询状态读取这张表。

对应页面环节：

- 点击生成全屋效果图。
- 生成队列。
- 生成中、完成、失败状态。

为什么需要：

- 图片生成通常不是瞬间完成，需要任务表承接异步流程。
- 用户刷新页面后，也能根据任务表恢复当前生成状态。
- 失败时可以保存错误原因，方便排查和重试。

字段建议：

- `id`：任务 ID，主键。
- `project_id`：所属项目 ID，关联 `design_projects.id`。
- `status`：任务状态，例如 `queued`、`running`、`completed`、`failed`。
- `progress`：任务进度，0 到 100。
- `prompt`：后端最终发送给图片生成模型的 prompt。
- `error_message`：失败原因。
- `started_at`：开始时间。
- `completed_at`：完成时间。
- `created_at`：创建时间。

### design_renders

保存生成出的效果图。

用途说明：

- 保存图片生成完成后的结果。
- 一次全屋方案会产生多张图，例如主图、客厅视角、卧室视角、厨房视角等。
- 中间大图、底部缩略图、放大预览都读取这张表。

对应页面环节：

- 全屋效果图方案。
- 多视角缩略图。
- 放大查看。
- 保存和导出。

为什么需要：

- 生成任务只代表任务过程，不能直接承载多张结果图。
- 每张图需要有自己的空间名、视角名、排序和缩略图。
- 后续用户查看历史方案时，需要从这里恢复图片结果。

字段建议：

- `id`：效果图 ID，主键。
- `project_id`：所属项目 ID，关联 `design_projects.id`。
- `job_id`：所属生成任务 ID，关联 `design_generation_jobs.id`。
- `space_name`：空间名称，例如全屋、客厅、主卧、厨房。
- `view_name`：视角名称，例如主视角、沙发视角、电视墙视角。
- `image_url`：高清效果图地址。
- `thumbnail_url`：缩略图地址。
- `sort_order`：排序值，用于控制展示顺序。
- `created_at`：创建时间。

### design_reviews

保存知识库检查结果。

用途说明：

- 保存“用知识库检查全屋方案”的结果。
- 检查内容包括施工风险、材料建议、预算风险、落地提醒等。
- 这是效果图模块和 AI 装修顾问知识库之间的桥接表。

对应页面环节：

- 用知识库检查全屋方案。
- 全屋方案检查结果。
- 施工、材料、预算风险展示。

为什么需要：

- 知识库检查结果需要独立保存，不能混在效果图图片表里。
- 同一个方案可能多次检查或更新检查结果。
- 后续用户回看历史方案时，也要能看到当时的检查建议。

字段建议：

- `id`：检查结果 ID，主键。
- `project_id`：所属项目 ID，关联 `design_projects.id`。
- `review_status`：检查状态，例如 `pending`、`completed`、`failed`。
- `risk_summary`：整体风险摘要。
- `material_suggestions`：材料建议。
- `construction_risks`：施工风险。
- `budget_risks`：预算风险。
- `created_at`：创建时间。

## API 建议

### 上传户型图

`POST /api/design/floor-plan`

职责：

- 接收户型图文件。
- 上传到 Supabase Storage。
- 创建 `design_projects` 和 `design_floor_plans`，或更新当前项目。
- 返回项目 ID、文件 URL、初始解析状态。

### 创建生成任务

`POST /api/design/jobs`

职责：

- 校验项目是否已有户型图。
- 读取用户生成意图和户型解析结果。
- 创建 `design_generation_jobs`。
- 返回 job ID。

### 查询生成任务

`GET /api/design/jobs/[id]`

职责：

- 返回任务状态、进度、错误原因。
- 如果任务完成，返回生成结果列表。

### 查询项目结果

`GET /api/design/projects/[id]/renders`

职责：

- 返回项目下所有效果图、缩略图、空间视角信息。

### 知识库检查方案

`POST /api/design/projects/[id]/review`

职责：

- 把户型解析、生成意图、方案说明、材料建议传给知识库检查逻辑。
- 输出施工、材料、预算和落地风险。

## 实施顺序

### Step 1：确认数据结构

目标：

- 按页面流程确认 5 张核心表。
- 明确每张表负责保存哪个页面环节的数据。

产物：

- `design_projects`
- `design_floor_plans`
- `design_generation_jobs`
- `design_renders`
- `design_reviews`

确认后进入 Step 2。

### Step 2：补 Supabase 建表 SQL

目标：

- 生成可直接在 Supabase SQL Editor 执行的 SQL。
- 包含主键、外键、状态字段、JSON 字段、时间字段和索引。
- 包含每张表和核心字段的数据库备注。

注意：

- 先建 `design_projects`。
- 再建依赖项目 ID 的其他表。
- SQL 需要支持重复执行时不报错。

SQL 文件：

- `infra/supabase/design-render-schema.sql`

执行方式：

1. 打开 Supabase 项目。
2. 进入 SQL Editor。
3. 复制 `infra/supabase/design-render-schema.sql` 全部内容。
4. 点击 Run 执行。
5. 确认 Table Editor 中出现 5 张表：
   - `design_projects`
   - `design_floor_plans`
   - `design_generation_jobs`
   - `design_renders`
   - `design_reviews`

确认后进入 Step 3。

### Step 3：创建 Supabase Storage bucket

目标：

- 创建户型图和效果图使用的存储 bucket。
- 至少需要支持户型图上传和生成图访问。

建议 bucket：

- `design-assets`

目录建议：

- `floor-plans/`
- `renders/`
- `thumbnails/`

当前约定：

- Bucket 名称：`design-assets`
- Public bucket：开启
- 户型图上传目录：`floor-plans/{project_id}/{file_id}`
- 效果图目录：`renders/{project_id}/{render_id}`
- 缩略图目录：`thumbnails/{project_id}/{render_id}`

说明：

- 当前先使用 public bucket 跑通上传和前端展示。
- 上传操作由后端 API 使用 Supabase service role 执行。
- 后续接用户登录和权限后，可以改成私有 bucket + signed URL。

具体操作：

1. 打开 Supabase 项目。
2. 左侧进入 `Storage`。
3. 点击 `New bucket`。
4. `Bucket name` 填写：

```text
design-assets
```

5. 打开 `Public bucket`。
6. `Restrict file size` 暂时关闭。
7. `Restrict MIME types` 暂时关闭。
8. 点击 `Create`。

为什么先开启 Public bucket：

- 当前阶段优先跑通上传和前端图片展示。
- 户型图和效果图后续需要直接在页面上预览。
- 真实权限控制后续再改为 private bucket + signed URL，避免第一阶段被权限配置卡住。

为什么暂时不限制文件大小和 MIME：

- 第一阶段文件大小和类型由后端 API 控制。
- 当前接口限制文件大小不超过 15MB。
- 当前接口只允许 JPG、PNG、WEBP、PDF。
- 后续稳定后可以在 Storage 层再加一层限制。

创建完成后的确认点：

- Storage 列表中能看到 `design-assets`。
- Bucket 标记为 public。
- 后端 API 使用的 bucket 名称和 Supabase bucket 名称完全一致。
- 名称必须是 `design-assets`，不要写成 `design_asset`、`design-assets/` 或其他变体。

当前后端上传路径：

```text
design-assets
└── floor-plans/
    └── {project_id}/
        └── {uuid}.{ext}
```

后续生成图片路径：

```text
design-assets
├── renders/
│   └── {project_id}/
│       └── {render_id}.{ext}
└── thumbnails/
    └── {project_id}/
        └── {render_id}.{ext}
```

常见问题：

- 如果上传 API 报 `Bucket not found`，说明 `design-assets` 没建成功或名字不一致。
- 如果上传成功但页面图片打不开，先检查 bucket 是否开启 Public。
- 如果数据库有记录但 Storage 没文件，检查上传 API 的 `storage_path` 和 Supabase Storage 文件列表。
- 如果前端提示文件类型错误，检查上传文件是否为 JPG、PNG、WEBP 或 PDF。

确认后进入 Step 4。

### Step 4：做上传户型图 API

目标：

- 前端上传户型图。
- 后端保存文件到 Supabase Storage。
- 后端写入 `design_projects` 和 `design_floor_plans`。
- 页面从待上传进入上传成功或解析中状态。

建议接口：

- `POST /api/design/floor-plan`

当前接口：

- 路径：`apps/web/src/app/api/design/floor-plan/route.ts`
- 请求格式：`multipart/form-data`
- 文件字段：`file`
- 可选字段：`intentText`

接口职责：

- 校验户型图文件是否存在。
- 限制文件类型为 JPG、PNG、WEBP、PDF。
- 限制文件大小不超过 15MB。
- 创建 `design_projects` 记录。
- 上传文件到 `design-assets/floor-plans/{project_id}/...`。
- 写入 `design_floor_plans` 记录。
- 返回 `project` 和 `floorPlan`。

确认后进入 Step 5。

### Step 5：前端接真实上传状态

目标：

- 上传按钮接真实文件选择。
- 未上传时禁用生成。
- 上传后展示文件名和解析状态。
- 户型解析结果从接口读取，不再写死。

当前实现：

- 文件：`apps/web/src/app/components/design-workspace.tsx`
- 上传按钮已接入真实文件选择。
- 接口：`POST /api/design/floor-plan`
- 文件字段：`file`
- 可选字段：`intentText`
- 上传中显示 `上传中...`。
- 上传成功后显示文件名和文件大小。
- 上传成功后自动进入解析，解析完成后生成按钮从禁用变为可点击状态。
- 上传成功后右侧户型解析从 `待上传后识别` 变为 `解析中`。
- 示例需求按钮会把示例内容填入 AI 生成意图输入框。

确认后进入 Step 5.5。

### Step 5.5：真实户型图解析

目标：

- 上传成功后自动进入解析中。
- 调用视觉模型解析户型图。
- 解析完成后回填户型、面积、空间、动线。
- 解析完成后才允许点击“生成全屋效果图”。

当前实现：

- 视觉模型调用：`apps/web/src/lib/ai/dashscope.ts`
- 解析接口：`POST /api/design/floor-plan/[id]/analyze`
- 路由文件：`apps/web/src/app/api/design/floor-plan/[id]/analyze/route.ts`
- 默认视觉模型：`qwen-vl-plus`
- 可通过环境变量 `VISION_MODEL` 覆盖。

状态流转：

```text
上传成功
-> design_floor_plans.analysis_status = pending
-> 前端自动调用解析接口
-> analysis_status = analyzing
-> 视觉模型返回 JSON
-> analysis_status = completed
-> design_projects.status = ready
```

回填字段：

- `design_floor_plans.house_type`
- `design_floor_plans.area`
- `design_floor_plans.spaces`
- `design_floor_plans.circulation`
- `design_floor_plans.analysis_result`
- `design_projects.house_type`
- `design_projects.area`

前端表现：

- 上传成功后显示 `解析中`。
- 解析中生成按钮禁用。
- 解析完成后右侧回填户型、面积、空间、动线。
- 解析完成后生成按钮启用。

当前限制：

- 第一版真实解析只支持 JPG、PNG、WEBP。
- PDF 可以上传保存，但解析接口会提示暂不支持直接解析 PDF。
- PDF 转图片后解析作为后续增强步骤。

确认后进入 Step 6。

### Step 6：做生成任务 API

目标：

- 用户点击生成全屋效果图后创建任务。
- 任务写入 `design_generation_jobs`。
- 前端轮询任务状态。

建议接口：

- `POST /api/design/jobs`
- `GET /api/design/jobs/[id]`

当前实现：

- 创建任务接口：`apps/web/src/app/api/design/jobs/route.ts`
- 查询任务接口：`apps/web/src/app/api/design/jobs/[id]/route.ts`
- 点击生成时创建 `design_generation_jobs`。
- 当前任务会调用真实生图服务生成全屋装修效果图。
- 生成图片上传到 Supabase Storage。
- 生成结果写入 `design_renders`。
- 成功后任务状态写入 `completed`，进度写入 `100`。
- 失败后任务状态写入 `failed`，并保存错误原因。

当前说明：

- 当前不使用 mock 图片。
- 未配置真实生图服务时，接口直接报错。
- 当前必须生成 `全屋 · 全屋效果图` 和若干空间效果图。

确认后进入 Step 7。

### Step 7：真实效果图生图闭环

目标：

- 后端基于户型解析结果和用户意图拼接 prompt。
- 调用真实图片生成模型。
- 图片保存到 Supabase Storage。
- 写入真实 `design_renders` 结果。
- 前端展示数据库返回的真实图片结果。

当前实现：

- 前端点击“生成全屋效果图”后调用 `POST /api/design/jobs`。
- 后端写入 `design_generation_jobs`。
- 后端调用 DashScope / 千问图片生成接口。
- 后端把生成图片上传到 `design-assets/renders/{project_id}/...`。
- 后端写入真实 `design_renders`。
- 前端展示大图、横向滑动缩略图、生成队列进度和放大预览。
- 当前不展示保存、导出、知识库检查操作按钮。

生成数量规则：

- 首轮只生成 1 张全屋效果图。
- 空间效果图来自户型解析结果。
- 解析出几个有效空间，页面就展示几个可生成入口。
- 用户点哪个空间，就生成哪个空间。
- 不默认补空间，不默认一次性生成全部空间。
- 空间图接口：`POST /api/design/jobs/{id}/spaces`。

确认后进入 Step 8。

### Step 8：真实生图服务配置

目标：

- Vercel 和本地环境都配置真实生图所需环境变量。
- 生图失败时可以明确定位是模型、网络、额度还是 Storage 问题。

当前环境变量：

- `DASHSCOPE_API_KEY`：必填，千问 / 通义真实生图服务密钥。
- `DASHSCOPE_IMAGE_MODEL`：可选，默认 `wan2.7-image`。
- `DASHSCOPE_IMAGE_SIZE`：可选，默认 `1K`。
- `DASHSCOPE_IMAGE_THINKING_MODE`：可选，默认 `false`，首轮快出图；需要更强推理时可设为 `true`。
- `DASHSCOPE_IMAGE_CREATE_URL`：可选，默认 `https://dashscope.aliyuncs.com/api/v1/services/aigc/image-generation/generation`。
- `DASHSCOPE_TASK_URL`：可选，默认 `https://dashscope.aliyuncs.com/api/v1/tasks`。
- `DASHSCOPE_IMAGE_TIMEOUT_MS`：可选，默认 `180000`。

确认后进入 Step 9。

- 检查结果写入 `design_reviews`。

## 注意事项

- 效果图生成模块不要复用 AI 装修顾问的聊天 UI。
- 知识库检查只能作为方案生成后的辅助能力。
- 不要在初始态展示假效果图或假解析结果。
- 不要让用户手动勾选生成空间，空间应来自户型图解析。
- 前端不要直接调用图片生成模型，统一走后端 API。
